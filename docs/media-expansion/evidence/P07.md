## Query plans and cost bounds

`discovery.integration.test.ts` seeds **100 shows / 20,300 episodes** (20,003 on the large show), runs the actual Drizzle queries with `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`, asserts at least five plans and sub-second single-query execution, and writes `/tmp/p07-query-plans.json`. Responses remain at 50 episodes maximum. The following measured run is reproducible with the command above:

| Query | Local execution time |
| --- | ---: |
| Show UUID detail | 0.030 ms |
| Large-show episode count/revision | 24.154 ms |
| First 50 episodes | 16.349 ms |
| Filtered show count/revision | 0.681 ms |
| Filtered show page | 0.628 ms |
| Verified globe markers | 0.278 ms |

Show/detail queries use existing media-item, feed/show/source and block indexes. At this deliberately skewed dataset PostgreSQL chooses sequential/hash processing for the large show's episode page and revision aggregate. No added index is justified by these timings; adding a sort index alone would not remove the revision aggregate cost. Paginated statements enforce a 1.5-second DB timeout; input sizes/offsets are capped. These warm, single-client synthetic measurements **do not establish** the 5,000/10,000-user capacity target. P14/P16 must revisit aggregate costs under measured concurrency.
